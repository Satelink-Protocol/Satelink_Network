## 1. ROOT CAUSE

Two compounding factors produced the near-vertical jump to the 1 GB ceiling:

1. **Chronic (the floor):** the RPC money path writes **1 `revenue_events_v2` row + 2 append-only
   `ledger_entries` rows per call** (double-entry; `ledger_entries.ref_type` is **100 %**
   `revenue_event`, 691,306 rows ≈ 2 × 345,822 revenue events). These are written for *every* call,
   **including unpaid free-tier calls**. The Aug 18–22 traffic surge grew this append-only ledger from
   the historical ~400 MB floor to its current 626 MB.
2. **Acute (the spike):** on **2026-08-22 a single-day write storm added 469,224 `ledger_entries`
   rows**. With `max_wal_size = 1024 MB` configured on a **1 GB** volume, transient WAL generated by
   that storm plus the heap crossed the ceiling → disk full → flat-line. A checkpoint/restart
   (`pg_stat_archiver.stats_reset = 2026-08-27 08:46 UTC` confirms a restart today) drained WAL back
   to 96 MB, and the operator resized the volume to **5 GB**.

**The M9 endurance driver is NOT the cause.** It died at **call 64** on **2026-08-21 08:33 UTC**
(6 days ago, 3 days *before* its planned exit gate), having made 64 of ~5000 planned calls. See §5.

## 3. WHAT I FIXED vs WHAT I DID NOT (and why)

**Fixed / delivered:** this incident doc; the byte attribution; the standing-rule guardrail in
`libs/CLAUDE.md`. **No data, schema, or Railway config was changed** — and that is the correct
outcome, because:

- **`ledger_entries` (301 MB, the biggest table) and `revenue_events_v2` are append-only by hard
  invariant** (`libs/CLAUDE.md` invariant 5: *"Ledger is append-only. No UPDATE, no DELETE"*;
  invariant 1: *balance is DERIVED from ledger entries*). A retention prune on them would corrupt every
  derived balance and is a **failed milestone**. Phase 2(C)'s "write a retention prune migration" is
  therefore **forbidden here** for the money-path tables that actually hold the bytes.
- **The only clear observability table is `node_health_logs` — 46,031 rows / 6.3 MB (~1 %).** Adding a
  new retention primitive + scheduled job to a **FROZEN** architecture (`libs/CLAUDE.md`: *"Do not add
  primitives. Do not expand scope."*) to reclaim 6 MB is not justified.
- **`max_wal_size` / `max_slot_wal_keep_size` are Railway/Postgres config**, and Claude Code scope is
  `apps/api` + `apps/web` only — **never Railway env/config**. Handed to the operator (§4).

**STOP conditions hit (awaiting operator decision):**

- **STOP-4 cleared:** Postgres is writable (not in recovery, temp INSERT OK). Normal playbook.
- **STOP-5 N/A:** no replication slots. WAL retention was config-driven, not a stuck slot.
- **STOP-1 (no prune executed):** the tables holding the bytes are append-only money-path; I did not
  DELETE/TRUNCATE anything.
- **STOP-2 (no VACUUM FULL / REINDEX):** not needed — bloat is negligible and the volume now has 4.4 GB
  free. The 112 MB of `revenue_events_v2` indexes *could* be trimmed by dropping redundant indexes
  (`request_id` is indexed 3× — see §4), but that is a reviewed schema change, not an emergency action.

## 7. GUARDRAILS (prevent recurrence)

1. **Cap WAL so it can never equal the volume again** (operator / Railway Postgres config):
   `max_wal_size = 512MB`, `max_slot_wal_keep_size = 256MB`, `min_wal_size = 80MB`. The Aug-22 spike
   only reached the ceiling because `max_wal_size` was 1 GB on a 1 GB volume.
2. **Volume headroom alerting** at 70 % / 85 % (operator) — this incident had no alert until 99 %.
3. **Stop ledgering unpaid free-tier calls** (the real growth driver). The money path writes 2
   append-only ledger rows + 1 revenue event per free-tier call that collects $0. Fixing this is the
   only lever that slows `ledger_entries` growth — but it touches the **FROZEN** money-path architecture
   and `free_tier_gate.js` is forbidden to modify, so it is a **founder decision**, not an autonomous
   change.
4. **Autovacuum tuning** on high-churn tables (`autovacuum_vacuum_scale_factor=0.05`,
   `autovacuum_vacuum_cost_limit=1000`) — operator, since these are money-path tables.
5. **Standing rule added to `libs/CLAUDE.md`** (this PR) so future agents never try to prune the ledger
   to reclaim disk.
